## LangChain

- **LangChain** is an open-source framework that simplifies building AI-powered applications by connecting LLMs with external data sources, memory, and automated workflows.
  - LangChain is stateless by default. It does not automatically track conversation history unless you explicitly configure a memory component.
- **`PromptTemplate`**:
  - **Structure:** A single, flat string template with variable placeholders (e.g., `"{topic}"`).
  - **Role Support:** None; it has no concept of speaker roles.
  - **Use Case:** Designed for older text-completion models (like GPT-3 or base LLMs) that take a single text string as input.
- **`ChatPromptTemplate`**:
  - **Structure:** A sequence or list of role-based message tuples or objects (e.g., `system`, `human`, `ai`).
  - **Role Support:** Explicitly defines who is speaking and sets behaviors (e.g., a `system` prompt to set personality, followed by `human` inputs).
  - **Use Case:** Built for modern chat models (like GPT-4 or Claude) that expect structured multi-turn conversations.

| Feature            | PromptTemplate         | ChatPromptTemplate                       |
| :----------------- | :--------------------- | :--------------------------------------- |
| **Input Format**   | Single text string     | List of message tuples/objects           |
| **Role Awareness** | No roles (flat text)   | Explicit roles (`system`, `human`, `ai`) |
| **Target Models**  | Text-completion models | Chat-based models                        |

- **Chain**: a sequence of components or operations connected to accomplish a specific task using an LLM.
  - Typically constructed with LCEL (LangChain Expression Language).
- **LCEL**: a declarative way to compose, connect, and execute LangChain components.
  - Done so with the pipe operator.
  - Output parsers are typically part of a chain; they convert LLM responses into a desired format (text, JSON, or structured objects).

## Chains vs. Agents

| Feature           | **Chains**                                       | **Agents**                                                                                        |
| :---------------- | :----------------------------------------------- | :------------------------------------------------------------------------------------------------ |
| **Logic Type**    | Deterministic (Pre-defined)                      | Non-deterministic (Dynamic)                                                                       |
| **Workflow**      | Step A $\rightarrow$ Step B $\rightarrow$ Step C | Input $\rightarrow$ LLM Decision $\rightarrow$ Action $\rightarrow$ Observation $\rightarrow$ ... |
| **Flexibility**   | Low (Follows a rigid path)                       | High (Can decide which tools to use)                                                              |
| **Complexity**    | Easier to debug and predict                      | Harder to control and monitor                                                                     |
| **Best Use Case** | Standardized, repeatable tasks.                  | Open-ended problem solving and tool usage.                                                        |

## Architecture

- **Input processing**: transform raw data into structured documents.
- **Embedding & storage**: convert text into searchable vector representations.
- **Retrieval**: find relevant information based on user queries.
- **Generation**: use AI models to create responses, optionally with tools.
- **Orchestration**: coordinate everything through agents and memory systems.

## LangChain vs. LangGraph vs. LangSmith

- **LangChain**: builds the AI application.
  - Model integrations.
  - Prompt templates.
  - Retrieval components.
  - Tools and agents.
- **LangGraph**: controls complex AI workflows.
  - Stateful agents.
  - Cyclic workflows.
  - Conditional execution.
  - Human-in-the-loop approvals.
  - Checkpoints and persistence.
- **LangSmith**: helps observe, debug, and evaluate those applications.
  - Execution tracing.
  - Debugging.
  - Prompt evaluation.
  - Performance monitoring.
  - Dataset-based testing.

## RAG

- **Retrieval-Augmented-Generation**: an AI system that enhances a LLM model by connecting it to external, authoritative, knowledge-bases before generating a response.
  - **Indexing & embedding**: reference documents, manuals, etc. are split into small chunks, converted into numerical vector embeddings, and stored in a specialized vector database.
  - **Retrieval**: when a user asks a question, the query is also turned into an embedding. The system searches the vector database to find the most semantically relevant text chunks.
  - **Augmentation**: the retrieved text chunks are injected into the prompt alongside the user's original question as context.
  - **Generation**: the LLM reads the augmented prompt and crafts a grounded, accurate, and context-specific final answer.
- You can still have a RAG app without vectorized data. Retrieving database records, and injecting that context, still counts.

## Vector DB

- **Vector**: a list of numbers that represents the meaning or characteristics of something.
- **Embedding**: the process of converting text, words, or tokens into a list of numbers (a dense numerical vector) that captures their semantic meaning.
- **Vector database**: a specialized database designed to store, search, and retrieve data based on meaning and similarity, rather than just exact words or matching values.
- We typically **chunk** groupings of text into embeddings, improving performance for retrieval.

| Database | Characteristics                                            |
| :------- | :--------------------------------------------------------- |
| Chroma   | Simple, developer-friendly, great for experimentation      |
| Pinecone | Managed cloud vector database                              |
| Milvus   | Designed for large-scale vector workloads                  |
| Weaviate | Vector search with additional data management capabilities |
| Qdrant   | High-performance vector search                             |
| FAISS    | Vector similarity search library from Meta                 |

## Memory Strategies

- **Conversation buffer memory**: stores the entire history of the conversation. Simple, but can quickly exceed the LLM's context window (token limit).
- **Conversation buffer window memory**: only keeps the last K exchanges. This keeps the context window usage constant but causes the model to forget anything older than the window.
- **Conversation summary memory**: uses an LLM to summarize the conversation history into a concise paragraph. This saves space while preserving the gist of the chat.
