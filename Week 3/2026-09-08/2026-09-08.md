## SQL

- **Relational Databases**:
  - Organized data in tables, with row and columns.
  - Usually, some flavor of SQL may be used to query and manipulate the database (e.g. MySQL, PostgreSQL, Oracle).
- **NoSQL Databases**:
  - Designed for handling unstructured, semi-structured, or rapidly changing data. (e.g. MongoDB, Cassandra, Redis).

## SQL

- Terms:
  - **Database**: top level container for application's data.
  - **Schema**: namespace inside a database.
  - **Table**: what stores the actual data.
  - **Columns**: defines the data type.
  - **Constraints**: puts limits on what data is allowed.
  - **Indexes**: optimizations that make queries faster.
  - **Views**: essentially a saved query.
  - **Functions**: reusable operation that lives in the database.
- Constraints:
  - `NOT NULL`: Ensures that a column cannot have a NULL value.
  - `UNIQUE`: Ensures that all values in a column are different.
  - `PRIMARY KEY`: A combination of a NOT NULL and UNIQUE. Uniquely identifies each row in a table.
  - `FOREIGN KEY`: Prevents actions that would destroy links between tables.
  - `CHECK`: Ensures that the values in a column satisfies a specific condition.
  - `DEFAULT`: Sets a default value for a column if no value is specified.
  - `CREATE INDEX`: Used to create and retrieve data from the database very quickly.
- Sub-languages:
  - **DDL**: `CREATE`, `DROP`, `ALTER`, `TRUNCATE`.
  - **DML**: `INSERT`, `UPDATE`, `DELETE`, `CALL`, `EXPLAIN CALL`, `LOCK`.
  - **TCl**: `COMMIT`, `SAVEPOINT`, `ROLLBACK`, `SET TRANSACTION`, `SET CONSTRAINT`.
  - **DQL**: `SELECT`.
  - **DCL**: `GRANT`, `REVOKE`.
- Three-Schema Approach:
  - **External** (conceptual): describes part of the database that a particular user group is interested in.
  - **Conceptual** (logical): describes the structure of the whole database including entities, relationships, data types, user operations, and constraints.
  - **Physical**: describes the physical storage structure of the database, i.e. storage medium, exact implementation details.
- **Unified Modeling Language** (UML):
  - Broad modeling language for software development.
  - Includes use case diagrams, class diagrams, deployment diagrams, etc.
- **Entity Relationship Diagram** (ERD):
  - Focused on relational database design.
  - Part of the conceptual/external stage.
- **ACID**:
  - **Atomicity**: treat a transaction as a single, indivisible unit. Either all operations within the transactions succeed, or none of them do.
  - **Consistency**: ensure the database transitions from one valid state to another, adhering to all defined rules, constraints, and triggers.
  - **Isolation**: guarantees that concurrent transactions do not interfere with each other, appearing as if they are executed sequentially.
  - **Durability**: guarantees that once a transaction is committed, its changes are permanent, even if the system crashes.

## ERD

![ERD](ERD.png)

- **Weak entity**: an entity with no key.
  - Must participate in an identifying relationship type w/ an owner or identifying entity.
- Attribute types:
  - **Simple (atomic) attributes**: data point that can’t be broken down further.
  - **Composite attributes**: composed of several components; uses `(parentheses)`.
  - **Single-valued**.
  - **Multi-valued**: multiple values in field, like a vector (e.g. 2-tone cars may have multiple entries in a `color` field); uses `{curly braces}`.
  - **Complex**: multi-valued & composite attributes nested arbitrarily.
  - **Derived**: gets its value from other fields; e.g. AGE can be calculated from today’s date + BDAY field.
  - **Stored**: stored in database; opposite of derived.
  - **NULL**.
- **Degree** (of a relationship): the number of entity sets (or tables) participating in that relationship.
- Structural constraints:
  - **Cardinality ratio constraint**: maximum number of relationship instances that an entity can participate in. Either: 1:N, N:1, 1:1, M:N.
  - **Participation constraint**: minimum number of relationship instances that each entity can participate in.
  - **Total participation**: every dept needs 1 or more employees and every employee must have at least 1 dept. Represented by a double line in ERD.
  - **Partial Participation**: 1 employee must manage each dept, but every employee need not be a manager. Represented by a single line in ERD.

## Normalization

- **1NF**: an attribute must only have atomic (simple, indivisible) values and that the value of any attribute in a tuple must be a single value from the domain of that attribute.
- **2NF**: each non-key column in a table is fully dependent on the primary key.
- **3NF**: each non-key column in a table is not transitively dependent on the primary key.
- We don’t always want normalization (not asked during QC):
  - **OLTP** (Online Transaction Processing):
    - APIs.
    - Usually very normalized.
  - **OLAP** (Online Analytical Processing):
    - Fewer, wider tables.
    - Usually denormalized.
