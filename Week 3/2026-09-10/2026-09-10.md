## Indexing

- Different underlying data structures will form depending on the index we use.
- The column that you use an index on should have a high level of uniqueness.
- B-Tree indexing is the default.
  - Good for any operation that uses: `=`, `<`, `<=`, `>`, `>=`, `BETWEEN`, `ORDER BY`, `LIKE 'prefix%;`.

## Partial Indexes

```sql
CREATE INDEX idx_users_active
ON my_schema.users (created_at)
WHERE is_active = True;

-- This query will be optimized and using our index. You MUST use `created_at` and `is_active` needs to be True
SELECT *
FROM my_schema.users
WHERE is_active = True
ORDER BY created_at DESC;
```

## GIN

- **Generalized Inverted Index** (GIN): solves problems b-trees can’t handle.
  - Query JSON, query array data, full text search.
  - Improved performance when querying JSON or arrays.
  - Containment queries: `@>`, `<@`, `&&`.

```sql
CREATE INDEX idx_customer_attributes
ON customer
USING GIN (attributes);
```

## Distinct and Unions

## Query Planner

- Decides how an SQL query is executed.
- It considers: indexes, join strategies, filters, etc.
- `EXPLAIN` shows the query plan **WITHOUT** running the query:
  - `EXPLAIN SELECT * FROM customer;`
  - Startup cost estimate (lower cost is better).
  - Total cost estimate (lower cost is better).
  - Estimated number of rows returned.
- The following actually runs the query and shows real execution times:
  - `EXPLAIN ANALYZE SELECT * FROM customer;`

## Triggers

- Database logic that runs automatically whenever a database event occurs (inserted, updated, deleted, truncated).
- Two components:
  - **Trigger function**: usually written in PL/pgSQL; returns a trigger, contains the logic.
  - **Trigger**: attached to a specific table, defines the event, calls the function.
  - Logic CANNOT be placed directly inside a trigger. You CANNOT attach a trigger without a trigger function.
- Two types:
- **Before triggers**: used for validation or automatically setting values; it can change the values on the triggering record.
- **After triggers**: used for logging, audits, syncing to other tables; you CANNOT change values of the triggering record.

| **Event** | **Available Variables** |
| --------- | ----------------------- |
| `INSERT`  | `NEW`                   |
| `UPDATE`  | `OLD`, `NEW`            |
| `DELETE`  | `OLD`                   |

```sql
CREATE OR REPLACE FUNCTION set_last_update()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    NEW.last_update = NOW();
    RETURN NEW;
END;
$$;

CREATE TRIGGER users_set_last_update
BEFORE UPDATE ON my_schema.users
FOR EACH ROW
EXECUTE FUNCTION set_last_update();
```

## Transaction Control Language (TCL)

- Controls how SQL statements are committed, undone, or partially rolled back.
- Transactions are a single running process that encapsulate changes to the DB.
- By default, Postgres runs in autocommit mode, so any DML is implicitly wrapped in BEGIN/COMMIT.
- TCL Clauses:
  - `BEGIN`: (`START TRANSACTION`): starts a transaction block.
  - `COMMIT`: make everything in the transaction permanent.
  - `ROLLBACK`: undoes everything since the last `BEGIN`.
  - `SAVEPOINT`: creates a checkpoint inside a transaction, we can rollback to a specific checkpoint.
- NoteRolling back to a checkpoint only rolls back records, not the state of the transaction. If any error occurs in a transaction, it will be ‘aborted’ and the entire transaction must be rolled back.
- You still need to implement exception handling so the transaction doesn’t get aborted and so you can enable partial updates to tables (ON CONFLICT in this example).

```sql
BEGIN;
DROP TABLE IF EXISTS tcl_demo;
CREATE TABLE tcl_demo (
    id   INT PRIMARY KEY,
    note TEXT
);
INSERT INTO tcl_demo VALUES (1, 'first row')
ON CONFLICT DO NOTHING;
SAVEPOINT sp1;
INSERT INTO tcl_demo VALUES (1, 'duplicate id')
ON CONFLICT DO NOTHING;
ROLLBACK TO SAVEPOINT sp1;
COMMIT;
```

# Multi-Version Concurrency Control (MVCC)

- MVCC is how PostgreSQL lets multiple transactions read and write data at the same time without blocking each other unnecessarily.
- Instead of locking rows for reads, postgres keeps multiple versions of each row and lets each transaction see the correct version based on its snapshot.
- When you update a row in PostgreSQL:
  - It does NOT overwrite the existing row.
  - It creates a new version.
  - The old version remains until no transaction needs it.
- When a transaction starts, it gets a snapshot:
  - A list of transaction IDs that were committed.
  - A list of ones still in progress.
- When reading a row, PostgreSQL checks hidden system fields:
  - Was xmin committed before my snapshot?
  - Is xmax empty (row not deleted)?
  - Was xmax committed after my snapshot?
    - If yes → you see it.
    - If not → it’s invisible to you.
- So every transaction sees a consistent view of the database at a point in time.
