## Unit Testing

- **Unit testing**: the practice of testing a small, isolated piece of software.
- **Isolation**: dependencies are often replaced with mocks to only test the method/class itself (i.e. test a service & mock the repository/DAO it uses).
- **Automation**: tests can be run repeatedly and automatically, such as when build the project or deploy.
- **Fast feedback**: since unit tests are small, they run quickly, allowing us to get fast feedback after code changes.
- Tests should be self-documenting, with clear naming conventions:
  - `calculateDiscount_for100Dollars_returns10Dollars`.
  - `add_shouldReturnSum`.
- Design pattern: injecting dependencies into service classes allows us to mock dependencies, rather than needing to test data access code directly.

| Test type           | What it tests                                                 | Typical speed | Example                                     |
| :------------------ | :------------------------------------------------------------ | :------------ | :------------------------------------------ |
| Unit                | One small unit of code                                        | Very fast     | Test Calculator.add()                       |
| Integration         | Multiple components working together                          | Medium        | Service + database                          |
| System / end-to-end | The complete application or a major workflow                  | Slow          | Log in → buy product → receive confirmation |
| Acceptance          | Whether the system meets specified business/user requirements | Often slower  | "A customer can successfully check out"     |

## Why Write Tests?

- Unit tests help us catch regressions.
- For example, imagine we write a test that checks whether a $100 purchase receives a $10 discount.
- Later, someone changes the implementation, and the test fails as a result.
- Without the test, the bug might not be discovered until much later.

## Structure of Test

- **Arrange**: set up what the test needs.
  - `Calculator calculator = new Calculator();`
- **Act**: perform the operation you are testing.
  - `int result = calculator.add(2, 3);`
- **Assert**: check the result.
  - `assertEquals(5, result);`

## JUnit

- Junit 5 is the modern implementation made up of:
  - **Junit platform**: the foundations for launching tests.
  - **Junit Jupiter**: the programming model and APIs most developers use to write Junit 5 tests.
  - **Junit vintage**: support for running older Junit 3 or 4 tests.
- **Maven Surefire**: the Maven plugin that discovers and runs tests during a Maven build.
- Hierarchy: Maven → Surefire Plugin → Junit Platform → Junit Jupiter → your `@Test` methods.

## Common JUnit Assertions

```java
assertEquals(expected, actual);
assertNotEquals(unexpected, actual);

assertTrue(condition);
assertFalse(condition);

assertNull(value);
assertNotNull(value);

assertThrows(
    SomeException.class,
    () -> someOperation()
);
```

## In-Memory Mocks vs Mockito

- **In-memory mocks** ("fake"): a lightweight, simplified implementation of a heavy external dependency (like a database, cache, or external API—that) runs entirely in the local Java application's memory (RAM) during testing.
  - Instead of routing traffic to a live resource, an in-memory mock actually simulates the stateful behavior of the real component using basic Java data structures.
- **Mockito**: mocking framework used to create simulated versions of objects that our code depends on.
  - This helps us test classes in isolation.

## JUnit Annotations

| Annotation    | Runs                               |
| :------------ | :--------------------------------- |
| `@BeforeEach` | Before each test                   |
| `@AfterEach`  | After each test                    |
| `@BeforeAll`  | Once before all tests in the class |
| `@AfterAll`   | Once after all tests in the class  |

## Stubs vs Mocks

- **Stub**: provides predefined answers so your test can focus on behavior.
- **Mock**: lets you verify interactions such as whether a method was called, what it returned, and with what arguments it used.
- Common methods:
  - `mock`(): creates the mock.
  - `when()`: configures the mock / sets up a stub.
  - `verify()`: verifies interactions with the mock (sometimes we only need this and no assertions, sometimes we could use both).
- General rules:
  - Use assertions when you care about the result/state.
  - Use `verify()` when you care about what the code did to a dependency.

## Naming Tests, Project Directory Placement, & POM Config

- Tests are placed in `src/test`, matching the structure of `src/main`.
- The name of the test classes should be the same as the original class but suffixed w/ `Test`.
- We must also add dependencies and plugin configuration to our Maven POM file.

## Testing Best Practices

- To ensure we write tests that are logically sound, consider the following different types of unit tests (non-exhaustive):
  - **Positive**: verifies code works when given valid inputs.
  - **Negative**: verifies the code works as expected with invalid inputs.
  - **Bulk**: verifies the code works when CRUD is performed on many records.
  - **Single**: verifies the code works when CRUD is performed on a single record.
  - **Access control** (positive/negative): verifies users do or do not have expected access to perform an action.

## TDD

- **Test driven development**: write unit tests before writing code.
