## Logging

- The process of recording information about what happens inside an application as it runs.
- Instead of using `System.out.println()` to print messages, applications typically use a logging framework to record events such as:
  - Application startup and shutdown.
  - User actions.
  - Errors and exceptions.
  - Database or network operations.
  - Debugging information.
  - Warnings about potential problems.

## SLF4J & Logback

- **SLF4J**: Simple Logging Facade for Java.
  - It is not itself a logging implementation.
  - Instead, it provides a common API that Java applications can use to write logs without being tied to a particular logging framework.
  - SLF4J is the interface we use for logging.
  - This allows you to change the underlying logging implementation without changing all of your application's logging code.

## Logback

- **Logback** is a logging implementation/framework for Java.
- It performs the work of processing log messages and deciding things such as:
  - Where logs should go.
  - Which log levels should be recorded.
  - How logs should be formatted.
  - Whether logs should be written to files.
  - When log files should be rotated.
- To set up Logback:
  - Add dependencies to `pom.xml`.
  - Configure the `logback.xml` file inside the `./src/main/resources` folder:
    - File or console output?
    - The log pattern printed to each line.
    - File rollover behavior.
    - Set minimum captured log levels.

```xml
<dependency>
    <groupId>org.slf4j</groupId>
    <artifactId>slf4j-api</artifactId>
    <version>2.0.17</version>
</dependency>
<dependency>
    <groupId>ch.qos.logback</groupId>
    <artifactId>logback-classic</artifactId>
    <version>1.5.18</version>
</dependency>
```

## Where Should We Log?

- Most logging occurs at the service layer (with the business logic):
  - "Order 1234 successfully placed".
  - "User password reset initiated for User ID: 1"
- Repository/DAO level logging:
  - Keep it lean.
  - Avoid boilerplate such as "Saving user to database".
  - Log custom complexity such as performance bottlenecks or specific database recovery logic.

## Logging Components

- Logback's core design revolves around three primary elements:
  - **Loggers**: The components you interact with to write logs. They are arranged in a named hierarchy (usually mapping directly to your Java package/class names).
  - **Appenders**: The destinations. They decide where the logs go—such as the console (`ConsoleAppender`), a file (`FileAppender`), or rotating files (`RollingFileAppender`).
  - **Encoders** The formatters. They transform the raw logging event into the final text string written by the appender (e.g., adding timestamps, thread names, and colors).

```xml
<?xml version="1.0" encoding="UTF-8"?>
<configuration>

    <!-- 1. Console Appender (for standard output) -->
    <appender name="STDOUT" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>

    <!-- 2. Rolling File Appender (for production logs) -->
    <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>logs/application.log</file>

        <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
            <!-- Daily rollover & compression -->
            <fileNamePattern>logs/application-%d{yyyy-MM-dd}.log.gz</fileNamePattern>
            <maxHistory>30</maxHistory> <!-- Keep 30 days worth of history -->
        </rollingPolicy>

        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>

    <!-- 3. Package-Specific Log Levels -->
    <logger name="com.example.repository" level="DEBUG" />

    <!-- 4. Root Logger (Default for everything else) -->
    <root level="INFO">
        <appender-ref ref="STDOUT" />
        <appender-ref ref="FILE" />
    </root>

</configuration>
```

## Log Levels

- `TRACE`: Highly detailed diagnostic info (finer-grained than `DEBUG`).
- `DEBUG`: Diagnostic info helpful for troubleshooting during development.
- `INFO`: General operational milestones (e.g., "Server started successfully", "User X logged in").
- `WARN`: Potential issues or non-critical anomalies that don't break the app yet.
- `ERROR`: Runtime errors, failures, or exceptions requiring immediate attention.
