## Inversion of Control (IoC)

- The approach of outsourcing the construction and management of objects.
- The Spring Container has two main responsibilities:
  - Create and manage objects (IoC).
  - Inject object dependencies (Dependency Injection).
- When it comes to configuring the Spring Container:
  - XML Configuration file (legacy).
  - Java annotations (modern).
  - Java source code (modern).
- SOLID:
  - Dependency inversion: the client delegates to another object the responsibility of providing its dependencies.
  - Give me a car → CarFactory.
  - CarFactory may need to assemble the car first (gather its dependencies).
  - We get a car without needing to provide its dependencies ourself.

## Types of Dependency Injection

- **Constructor injection**:
  - Use this when you have required dependencies.
  - Generally recommended by the Spring development team as the first choice.
  - This form of dependency injection is accomplished when a class receives its dependencies through its constructor during the instantiation process.
- **Setter injection**:
  - Generally not recommended because it's harder to test.
  - Use this when you have optional dependencies.
  - If dependency is not provided, your app can provide reasonable default logic.
  - This type of dependency injection happens when a class receives its dependencies through setter methods after it has been constructed.
- **Field injection**:
  - Generally less recommended.
  - Happens when dependencies are injected directly into the fields of a class, bypassing the constructor or setters.
  - It reduces the amount of boilerplate code, as no explicit setter or constructor is needed.
  - BUT, it makes your classes harder to test because you can't easily replace the dependencies with mocks.
  - It also breaks encapsulation because you're modifying private fields outside of the class.

## Spring Auto Wiring

- This is a convention-based approach.
- Spring will look for a class that matches (by class or interface).
- Spring will then inject it automatically, hence `Autowired`.
- **Component scanning**: Spring scans for `@Component` and automatically loads the correct class.
- **Spring Bean**: classes marked as `@Component` can automatically be instantiated.
- If we only have a single constructor, `@Autowired` is technically optional.
- `@Component` is a catch-all:
  - Other annotations can better describe intent (`@Service`, `@Repository`, etc.).

```java
@Component
class Engine {
    void start() { out.println("Engine started"); }
}

@Component
class Car {
    private final Engine engine;

    @Autowired
    Car(Engine engine) { this.engine = engine; }

    void drive() {
        engine.start();
        out.println("Car is driving");
    }
}

@SpringBootApplication
public class App {
    public static void main(String[] args) {
        ApplicationContext context =
            SpringApplication.run(App.class, args);
        Car car = context.getBean(Car.class);
        car.drive();
    }
}
```

## More Component Scanning

- `@SpringBootApplication` is composed of:
  - `@EnableAutoConfiguration`, `@ComponentScan`, `@Configuration`.
- By default, `@ComponentScan` is only applied to the starter package, i.e. `com.spring.demo`.
- That means no packages outside of this root package will get their components scanned.
- If our main package is `com.spring.demo` then those components will be scanned by default.
  - The `com.example.another` package will NOT automatically have its components scanned.
  - We can fix this by setting `scanBasePackages`:

```java
package com.spring.demo;

@SpringBootApplication(
    scanBasePackages = {"com.spring.demo", "com.spring.another"}
)
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}
```

| Annotation                 | Description                                                                         |
| :------------------------- | :---------------------------------------------------------------------------------- |
| `@EnableAutoConfiguration` | Enables Spring Boot's auto-configuration                                            |
| `@ComponentScan`           | Enables component scanning of current package (also recursively scans sub-packages) |
| `@Configuration`           | Able to register extra beans with `@Bean` or import other config classes            |

## Choosing Correct Implementation to Inject

#### `@Qualifier`

- We need to supply the Bean ID to `@Qualifier`.
- The Bean ID is always the name of our class, with the first letter in lowercase.
- This works the same for setter injection too.

```java
import org.springframework.beans.factory.annotation.Qualifier;

@RestController
public class MyFirstController {
    private Coach myCoach;

    @Autowired
    public MyFirstController(@Qualifier("coachImpl") Coach c) {
        myCoach = c;
    }
}
```

#### `@Primary`

- Leaves it up to the classes to determine which one to use.
- You can only have a single `@Primary` made available for injection.
- `@Qualifier` takes priority but you can still mix it with `@Primary`.
- In general, stick with `@Qualifier` as it is more specific and takes priority.

```java
import org.springframework.context.annotation.Primary;
import org.springframework.stereotype.Component;

@Component
@Primary
public class CoachImpl implements Coach {}
```

## Lazy Instantiation

- By default, Spring will load and initialize all beans, even if they aren't injected anywhere.
- We can set the `@Lazy` annotation onto a bean so the class isn't initialized until it is needed.
- Alternatively, we can set `spring.main.lazy-initialization=true` in `application.properties` to enable it for all classes.
- Make sure you have enough memory once all objects are loaded before worrying about optimization with lazy instantiation.

## Bean Scope

- By default, the Spring Container only creates on instance of a bean (a Singleton).
- It is cached in memory and all dependency injections will reference the SAME bean.

| Scope         | Description                                                    |
| :------------ | :------------------------------------------------------------- |
| `singleton`   | Create a single shared instance of the bean (default scope).   |
| `prototype`   | Creates a new bean instance for each container request.        |
| `request`     | Scoped to an HTTP web request (only used for web apps).        |
| `session`     | Scoped to an HTTP web session (only used for web apps).        |
| `application` | Scoped to a web app `ServletContext` (only used for web apps). |
| `websocket`   | Scoped to a web socket (only used for web apps).               |

## Prototype Scope

```java
import org.springframework.beans.factory.config.ConfigurableBeanFactory;
import org.springframework.context.annotation.Scope;
import org.springframework.stereotype.Component;

@Component
@Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
public class CoachImpl implements Coach {}
```

## Bean Lifecycle

1. Container started.
2. Bean instantiated.
3. Dependencies injected.
4. Internal Spring processing.
5. Custom init method.
6. Bean ready for use.
7. Container shutdown.
8. Custom destroy method.
9. Stop.

## Bean Lifecycle Methods

- `@PostConstruct`:
  - Set up handles to resources (databases, sockets, files, etc.).
- `@PreDestroy`:
  - Clean up handles to resources.
  - Prototype scoped beans will NOT call `@PreDestroy` methods.

```java
import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;

@Component
public class CoachImpl implements Coach {
    @PostConstruct
    public void doStartupStuff() {
        out.println("Doing startup stuff");
    }

    @PreDestroy
    public void doDestroyStuff() {
        out.println("Doing destroy stuff");
    }
}
```

## Configuration via Source Code

- Use `@Configuration` & `@Bean` if you don't want to use `@Component` for your bean.
- The `@Configuration` class gets full control.
- We can now pass parameters into our bean, set fields, manually set dependencies, etc.
- Why?
  - You may want to make an existing third-party class available but may not have access to the source code of it.
  - Real world example:
    - Setup an AWS S3 client as a Spring Bean in your app.
    - We can't modify the AWS SDK source code
    - We can't just add `@Component`.
    - We can configure it as a Spring bean, so we can use it across our app.

```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

// No `@Component`
public class CustomBean {
    public CustomBean(int a, int b) {
        // Custom Logic
    }
}

@Configuration
public class SportConfig {
    @Bean
    public Coach swimCoach() { // Method Name MUST Be The Bean ID
        return new SwimCoach(1, 2);
    }
}
```
