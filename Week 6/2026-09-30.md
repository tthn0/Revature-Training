## Hibernate

- A framework for persisting Java objects in a database.
- **Object-Relational Mapping** (ORM):
  - Bridges the gap between the object-oriented world of Java and the relational world of SQL databases.
  - Allows storing & retrieving Java objects directly as database tables and rows without writing complex, boilerplate SQL queries.
- Benefits:
  - Productivity boost: eliminates massive amounts of tedious JDBC code, connection management, and manual result-set mapping.
  - Database independence: by abstracting SQL dialects, Hibernate allows your application to switch underlying databases with minimal configuration changes.
  - Built-in caching: features a first-level cache (associated with the Session) and an optional second-level cache (shared across sessions) to significantly reduce database round-trips and improve performance.
  - Automatic transaction management: handles database transactions and connection pooling efficiently, ensuring data integrity.

## JPA

- Jakarta Persistence API (previously known as Java Persistence API).
- Standard API for Java ORMs.
- Is a specification & includes interfaces.
- Requires implementations to use.
- In Spring Boot, Hibernate is the default implementation of JPA.
- EclipseLink is another implementation of JPA.

## EntityManager vs JpaRepository

- **EntityManager** is the low-level JPA API for directly managing entities and interacting with the persistence context.
- **JpaRepository** is a Spring Data abstraction that gives you a ready-made repository with CRUD, pagination, sorting, and query methods—without writing most of the boilerplate yourself.
- **Java Persistence Query Language** (JPQL): used for querying entities and their fields, rather than database tables and columns, part of JPA standard and can be used by any JPA provider, i.e. Hibernate, EclipseLink, etc.
- Hibernate Query Language (HQL): Operates similar as above, but is Hibernate specific and thus may come with features unique to Hibernate.

| Feature                         | EntityManager                    | JpaRepository                         |
| :------------------------------ | :------------------------------- | :------------------------------------ |
| **Comes from**                  | JPA                              | Spring Data JPA                       |
| **Abstraction level**           | Low                              | High                                  |
| **CRUD boilerplate**            | You write it                     | Mostly provided                       |
| **Custom JPQL**                 | Directly                         | `@Query`, specifications, etc.        |
| **Persistence-context control** | Excellent                        | Limited/direct access not its purpose |
| **Pagination/sorting**          | Manual                           | Built in                              |
| **Derived queries**             | No                               | Yes                                   |
| **JPA portability**             | Yes                              | Tied to Spring Data                   |
| **Best for**                    | Complex/custom persistence logic | Typical application CRUD              |

## Stereotype Annotations

- **`@Component`**: the main stereotype annotation.
  - It is a class-level annotation.
  - Used across the application to mark the beans as Spring's managed components.
- **`@Service`**: a specialization of `@Component`.
  - The business logic of an application exists in the service layer.
  - Used to indicate that a class belongs to the service layer.
- **`@Repository`**: a specialization of `@Component`.
  - Very similar to the DAO pattern.
  - DAO classes provide CRUD operations for database tables.
- **@RestController**: a specialization of `@Component`.
  - Inherits `@Controller`.
  - Indicates that a particular class is a web service controller that returns data.
  - Mostly used with Spring MVC applications and is used in combination with `@RequestMapping` annotation.
  - The dispatcher scans the class and detects methods with HTTP annotations:
    - `@GetMapping`.
    - `@PostMapping`.
    - `@PutMapping`.
    - `@DeleteMapping`.

## Transaction

- The `@Transactional` annotation provides declarative transaction management in Spring, simplifying the process.
- When you apply it to a method or class, it instructs Spring to manage the transaction automatically:
  - Method-level: runs only the annotated method within a transactional context.
  - Class-level: runs all public methods within the class in a transactional context.
- You can customize `@Transactional` to control aspects of transaction behavior:
  - **Propagation**:
    - Defines how transactions behave when a method calls another transactional method..
  - **Isolation level**:
    - Sets how isolated a transaction is from other concurrent transactions.
    - `READ_COMMITTED`,` REPEATABLE_READ`, `and SERIALIZABLE`.
  - **Rollback rules**:
    - Define the conditions under which the system rolls back a transaction.
    - The `rollbackFor` and `noRollbackFor` attributes specify which exception types trigger or skip a rollback.
  - It's more common to just use `readOnly` instead of specifying the options above.
    - This disallows create, update, or delete operations and improves the performance of read-only transactions

### Transactional Propagation Strategies

- `REQUIRED`: joins an active transaction if one exists, otherwise starts a new one. (Default behavior)
- `SUPPORTS`: joins an active transaction if one exists; runs without a transaction otherwise.
- `MANDATORY`: joins an active transaction if one exists; throws an exception if there is none.
- `NEVER`: throws an exception if an active transaction exists.
- `NOT_SUPPORTED`: pauses any active transaction and runs without a transactional context.
- `REQUIRES_NEW`: always starts a new transaction. If an active transaction exists, Spring suspends it until this method completes.
- `NESTED`: starts a new transaction if none exists. If one exists, Spring creates a savepoint and can roll back to that savepoint if an exception occurs.

## Dirty Checking

- **Dirty checking** is an automatic feature in Spring Data JPA (via Hibernate) that tracks changes made to persistent entities inside an active transaction.
  - When the transaction commits, Hibernate compares the entity's current state to its original snapshot.
  - If it finds changes ("dirt"), it automatically executes an UPDATE query for you, meaning you don't have to manually call a `.save()` method.

## Mapping JPA Relationships

- We supply these on `@Entity` fields to map relationships between entities.
  - `@OneToOne`.
  - `@OneToMany`.
  - `@ManyToOne`.
  - `@ManyToMany`.

### 1:N Relationship

- We initialize `@OneToMany` collections with `ArrayList` so that it can never be `null` (best practice).
- `mappedBy`: allows us to use dot notation to reach a student's school (e.g. `someStudent.school`).
- `@JoinColumn`: defines the database field to use to tie the primary key of the other table.

```java
// School.java
@OneToMany(
  mappedBy = "school",
  fetch = FetchType.LAZY
)
private List<Student> students = new ArrayList<>();

// Student.java
@ManyToOne
@JoinColumn(name = "school_id")
private School school;
```

### N:M Relationship

- N:M relationships may be mapped with `@ManyToMany`.
  - However, this doesn't allow us to create fields on the underlying junction table.
- It's common to create a domain model for the junction object manually, and then use `@ManyToOne` and `@OneToMany` to tie all three tables together.

#### `orphanRemoval` (Database/JPA Layer)

- `orphanRemoval=true` is an attribute you can set inside the `@OneToMany` or `@OneToOne` JPA annotations.
- It tells Hibernate that if a child entity is removed from the parent's collection (or disassociated from the parent), that child should be automatically deleted from the database.
- How it differs from `Cascade.REMOVE`:
  - `cascade=CascadeType.REMOVE` deletes children only when the entire parent is deleted.
  - `orphanRemoval=true` deletes children if they are unlinked from the parent, even if the parent stays alive.
- Common use case: child entities that cannot exist independently without their parent.
  - For example, order items in an order; if you remove an item from the cart/order, it should be deleted from the database.

#### `cascade` (Database/JPA Layer)

- The cascade attribute inside `@OneToMany` (or `@ManyToOne`, etc.) defines how database operations performed on a parent entity should propagate down to its associated child entities.
  - Instead of manually saving or deleting every child entity individually, cascading does it automatically.
  - `CascadeType.PERSIST`: saves child entities automatically when the parent is saved.
  - `CascadeType.MERGE`: updates child entities automatically when the parent is updated.
  - `CascadeType.REMOVE`: deletes child entities automatically when the parent is deleted.
  - `CascadeType.ALL`: shorthand for applying all cascade operations.
- Common use case: when creating a new `Order` with multiple `OrderItems`, saving the `Order` automatically saves all the `OrderItems` without needing a separate `orderItemRepository.save()` call for each one.

## JpaRepository

- **EntityManager** is one API to interact with our database, it has a lower level of abstraction and thus, more control.
- **JpaRepository** is another API to interact with our database, it has a higher level of abstraction and thus, less control.
- Benefits of JpaRepository:
  - We simply create an interface that extends JpaRepository, and then we get CRUD methods out of the box.
  - Before, we had: Service → DAO Interface → Concretion (had to write boilerplate for CRUD).
  - Now we have: Service → Repo Interface (extends JpaRepository) with no extra code for common CRUD.

```java
// Generic: <Entity, EntityIdDataType>
public interface StudentRepo extends JpaRepository<Student, Integer> {}
```

### Out-Of-The-Box Methods

| Method            | Parameters              | Return type         | What it does                   |
| :---------------- | :---------------------- | :------------------ | :----------------------------- |
| `existsById(123)` | Integer id              | `boolean`           | Checks whether a record exists |
| `count()`         | none                    | `long`              | Counts all records             |
| `findAll()`       | none                    | `List<Student>`     | Gets all students              |
| `findById(123)`   | Integer id              | `Optional<Student>` | Gets one student by ID         |
| `save(student)`   | Object: Student student | `Student`           | Inserts or updates             |
| `delete(student)` | Object: Student student | `void`              | Deletes a student              |
| `deleteById(123)` | Integer id              | `void`              | Deletes by primary key         |
| `deleteAll()`     | none                    | `void`              | Deletes all students           |

- When using `findById()`, you can chain `orElseThrow()`.

### Derived Query Methods

- **Derived query methods**: JPA parses the method name according to strict naming conventions and automatically generates the underlying JPQL/SQL at runtime:
  - **Prefix**: determines the operation type (`find`, `read`, `query`, `get`, `count`, `exists`, `delete`, `remove`).
    - `find`, `read`, `query`, `get` are all synonyms doing the exact same thing.
  - **Subject**: optional return modifiers (e.g., `Distinct`, `First3`, `Top`).
  - **By**: the separator keyword that transitions from the operation to the criteria.
  - **Criteria**: property names combined with comparison keywords (`And`, `Or`, `LessThan`, `Like`, etc.).
- Examples:
  - Basic property matching:
  - `findByEmail(String email)`
  - `findByActiveTrue()`
  - `findByAgeEquals(Integer age)`
- Comparison operators:
  - `findByAgeGreaterThan(Integer age)`
  - `findByAgeLessThanEqual(Integer age)`
  - `findByBirthDateAfter(LocalDate date)`
  - `findBySalaryBetween(Double min, Double max)`
- Logical operators:
  - `findByFirstNameAndLastName(String first, String last)`
  - `findByAgeLessThanOrActiveTrue(Integer age)`
  - `findByDepartmentAndAgeGreaterThan(String dept, Integer age)`
- String & pattern matching:
  - `findByLastNameStartingWith(String prefix)`
  - `findByEmailEndingWith(String suffix)`
  - `findByNameContaining(String infix)`
  - `findByUsernameLike(String pattern)`
  - `findByFirstNameIgnoreCase(String name)`
- Nullability & boolean checks:
  - `findByPhoneNumberIsNull()`
  - `findByDeletedAtIsNotNull()`
  - `findByActiveIsTrue()`
- Ordering results:
  - `findByDepartmentOrderByLastNameAsc(String dept)`
  - `findByActiveTrueOrderByAgeDesc()`
- Limiting results:
  - `findTop3ByOrderBySalaryDesc()`
  - `findFirstByDepartmentOrderByHireDateAsc(String dept)`
  - `queryDistinctByLastName(String lastName)`
- Counting & deleting:
  - `countByDepartment(String dept)`
  - `existsByEmail(String email)`
  - `deleteByActiveFalse()`
  - `removeByAgeGreaterThan(Integer age)`

### Traversing Relationships

- Underscores allow us to traverse relationships.
- You can traverse through multiple levels of relationships.
- Can use `@Query` to create custom solutions when relationship traversal via derived query methods gets too complex.

```java
// Controller
@GetMapping(params = "schoolName")
public List<Student> getStudentsBySchoolName(@RequestParam String schoolName) {
  return studentService.findStudentsBySchoolName(schoolName);
}

// Service
@Transactional(readOnly = true)
public List<Student> findStudentsBySchoolName(String name) {
  return studentRepo.findBySchool_Name(name);
}

// DAO/Repo
public interface StudentRepository extends JpaRepository<Student, Integer> {
  List<Student> findBySchool_Name(String schoolName);
  List<Student> findByEnrollments_Course_Name(String courseName);
}
```

### `@Query`

- Used for writing JPQL when derived query methods aren’t enough.
- Great for complex queries.

```java
public interface StudentRepository extends JpaRepository<Student, Integer> {
  @Query("""
    SELECT s
    FROM Student s
    WHERE s.lastName = :lastName
    ORDER BY s.id ASC
    """)
  List<Student> findByLastName(
    @Param("lastName") String lastName
  );
}
```

| Approach     | Definition                                     | Common APIs in Spring                                    | Queries against                     |
| ------------ | ---------------------------------------------- | -------------------------------------------------------- | ----------------------------------- |
| HQL          | Hibernate Query Language                       | `Session`, `EntityManager`, `@Query`                     | Entity classes and their properties |
| JPQL         | Jakarta Persistence Query Language             | `EntityManager`, `@Query `                               | Entity classes and their properties |
| Native SQL   | Database's actual SQL dialect                  | `EntityManager`, `Session`, `@Query(nativeQuery = true)` | Database tables and columns         |
| Criteria API | Java API for building queries programmatically | `EntityManager`, `CriteriaBuilder`, `CriteriaQuery`      | Entity classes and their properties |

## Native SQL

```java
// Entity Manager
String sql = """
  SELECT *
  FROM employees
  WHERE salary > :salary
  """;
List<Employee> employees = entityManager
  .createNativeQuery(sql, Employee.class)
  .setParameter("salary", 50000)
  .getResultList();

// JpaRepository
public interface EmployeeRepository
  extends JpaRepository<Employee, Long> {
  @Query(
    value = "SELECT * FROM employees WHERE salary > :salary",
    nativeQuery = true
  )
  List<Employee> findHighEarners(
    @Param("salary") BigDecimal salary
  );
}
```
