## Kafka

- Decouples our data streams and systems.
  - **Producers** send (publish) messages to Kafka topics.
  - **Consumers** read (subscribe) messages from Kafka topics.
- Distributed, resilient architecture, fault tolerant.
- Horizontal scalability:
  - Can scale to 100s of brokers.
  - Can scale to millions of messages per second.
  - High performance latency (less than 10ms).

## The Problem It Solves

- (4 source systems) × (6 target systems) = (24 integrations).
- Each integration could be different:
  - Protocols (TCP, HTTP, REST, FTP, JDBC).
  - Data formats (CSV, JSON, etc.).
  - Schemas.

## Use Cases

- Messaging system.
- Activity tracking.
- Gather metrics from many locations.
- Application logs gathering.
- Stream processing (with Kafka Streams API).
- De-coupling of system dependencies.
- Integrations with Spark, Flink, Storm, Hadoop, and many other Big Data Technologies.
- Micro-services pub/sub.

## Real Life Examples

- Netflix uses Kafka to apply recommendations in real-time while you’re watching.
- Uber uses Kafka to gather user, taxi, and trip data in real-time to compute and forecast demand, and compute surge pricing.
- LinkedIn uses Kafka to prevent spam and collect user interactions to make better connection recommendations in real time

## Kafka Topics

- Kafka topics are streams of data.
- Like a table in a database (without any constraints).
- You can have as many topics as you want.
- Any kind of message format: JSON, CSV, Text, Binary (Images, PDF, MP4, etc.).
- The sequences of messages in a topic are called a data stream
- You don’t query topics; instead, producers/consumers handle it.

## Partitions & Offsets

- Topics are split into partitions.
- You can have as many partitions per topic as you want.
- Messages within each partition are ordered.
- **Offset**: each message gets an incremental ID.
- Topics are immutable: once data is written to them, it cannot be changed.
- Data is kept only for a limited time (default is one week, but it's configurable).
- Offsets only have meaning for a specific partition:
  - Offset 3 in partition 0 doesn’t represent the same data as Offset 3 in partition 1.
  - Offsets are not re-used even if previous messages have been deleted.
- Order is guaranteed only within a partition (not across partitions).
- Data is assigned randomly to a partition unless a key is provided.
- If a key is provided, it will be hashed to determine the correct partition.

### Message Anatomy

- Key (nullable binary).
- Value (nullable binary).
- Compression type.
- Headers (key-value pairs).
- Partition + offset.
- Timestamp (system set or user set).

## Producers

- Producers know which partition to write to (and which Kafka broker has it).
- In case of broker failures, producers will automatically recover.
- Message Keys:
  - Producers can choose to send a message key (string, number, binary, etc.).
  - If key == null, data is sent round robin (partition 0, then partition 1, etc.).
  - If key != null, then all messages for that key will always go to the same partition (uses hashing strategy).
  - A key is typically sent if you need message ordering for a specific field (e.g., a truck's ID).

## Consumers

- Consumers read data from a topic.
- Consumers automatically know which broker to read from.
- In case of broker failures, consumers know how to recover.
- Data is read in order from low to high offset within each partition.

## Consumer Offsets

- Kafka stores the offsets at which a consumer group has been reading.
- The offsets committed are in a topic named `__consumer_offsets`.
- When a consumer has processed data received, Kafka will automatically periodically commit the offsets.
- If a consumer dies, it will be able to read back from where it left off.
  - Since commits occur after polling rather than after code processing, a crash before code execution finishes will skip messages that were already marked as read, leading to data loss.
  - Solution for critical apps: developers often disable this (`enable.auto.commit = false`) to manually commit offsets only after data is successfully processed.

## Consumer Groups

- All the consumers in an application read data as a consumer group.
- Each consumer within a group reads from exclusive partitions.
- If you have more consumers than partitions, some consumers may be inactive.
- It's acceptable to have multiple consumer groups on the same topic.
- Often makes sense to have one group per service. (i.e., truck location service & truck notification service).
- To create distinct consumer groups, use the consumer property `group.id`.

## Message De/Serializer

- Kafka only accepts bytes as an input from producers and sends bytes out as output to consumers.
- They are used on values and keys.

## Brokers

- A Kafka cluster is composed of multiple brokers (servers).
- Each broker is identified with its ID (integer).
- Each broker contains certain topic partitions.
- A good number to get started is 3 brokers, but some big clusters have over 100 brokers.
- Every broker is also called a **bootstrap server**.
  - After connecting to any broker (bootstrap broker), you will be connected to the entire cluster.
  - That broker will send back to the client the metadata of all other brokers, topics, and partitions.

## CLI Commands

### Topics Management (`kafka-topics.sh`)

```bash
# Create Topic
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create \
  --topic user-events

# Delete Topic
kafka-topics.sh --bootstrap-server localhost:9092 \
  --delete \
  --topic user-events

# List Topics
kafka-topics.sh --bootstrap-server localhost:9092 --list
```

### Producing Messages (`kafka-console-producer.sh`)

```bash
# Produce Message
kafka-console-producer.sh --broker-list localhost:9092 \
  --topic user-events

# Produce Message w/ Key
kafka-console-producer.sh --broker-list localhost:9092 \
  --topic user-events \
  --property parse.key=true \
  --property key.separator=,
```

### Consuming Messages (`kafka-console-consumer.sh`)

```bash
# Consume All Messages From Offset 0
kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic user-events \
  --from-beginning
```
